# ADR-001: Apply each import in one database transaction

**Status:** accepted · **Date:** 2026-10-07

## Context

Every month the manager uploads the Network's base export (about 2,300 rows, one per line). The
MVP deleted every customer, account and line, then inserted the file again row by row from the
browser's server action. Customer IDs changed every month, so interaction history pointed at
customers that no longer existed, and a bad row stopped the run half-way with no error shown,
leaving a half-loaded base. We need an import that can be re-run safely, keeps history, reports
the rows it cannot trust, and either applies a whole file or none of it.

Supabase's REST API runs each request in its own transaction, so a sequence of upserts from the
app cannot be rolled back as a unit.

## Options

1. **Upserts from the app through the REST API, in batches.** Simple and visible in the app code,
   but a failure part-way leaves a partial import, and a crash between "update lines" and "mark
   missing lines as ported" corrupts the month.
2. **A direct Postgres connection from the app (`pg`) with BEGIN/COMMIT.** Real transactions, but
   it needs the database password in the app's environment and a connection pooler on serverless
   hosting, and the import code would bypass RLS entirely.
3. **Parse and normalise in the app, apply in one Postgres function (`import_base`).** The app
   does the messy work in plain, unit-tested TypeScript (phones to E.164, dates, duplicates,
   quarantine), then calls one RPC with the clean rows. The function runs in one transaction,
   checks the caller is a manager, and upserts by natural keys.

## Decision

Option 3. The function is `SECURITY DEFINER` with an explicit manager check, so the request runs
with the manager's own session (no server key in the app). It upserts customers (account number,
then registration number, then normalised name), accounts (account number) and lines (E.164
number), only touching rows whose values changed; marks lines missing from the file as ported
(never deletes them); stores the quarantine report; and re-matches the opt-out list to any new
customers. Any error rolls the whole file back. A structure change is caught in the app before
the database is called, and the failed attempt is logged so the manager sees it.

## Consequences

- Re-uploading a file changes nothing, and customer IDs (and so history) are stable.
- Business logic is split across TypeScript (parsing) and SQL (applying). Tests cover both:
  unit tests for the parsing, database tests (`npm run test:db`, also in CI) for the function.
- One RPC carries the whole file (about 1 MB of JSON). That is fine at this size; a much larger
  base would need staging tables and a chunked upload.
- A file that would mark more than a quarter of active lines as ported is refused as a probable
  partial export. If the base really shrinks that much, a manager has to change the threshold.
